# SmartStaccer contract reference

Field-level reference for `contracts/smart_staccer.tact`. For the product context and the reasoning behind the design, read the [README](../README.md) first.

The contract is a single actor: it holds sale records, accrues per-creator balances, and moves USDT jettons out. It has no upgrade path, no owner-controlled withdrawal of creator funds, and no pause. All token amounts are in USDT base units (**6 decimals**), so `1.00 USDT` is `1_000_000`.

## Storage

| Field | Type | Purpose |
|---|---|---|
| `admin` | `Address` | The only address permitted to register sales and to trigger gas-paid withdrawals |
| `usdtWalletAddress` | `Address` | The contract's own USDT jetton wallet; every transfer is sent here |
| `sales` | `map<Int, SaleRecord>` | Open sales awaiting their lock to expire, keyed by admin-supplied `saleId` |
| `availableBalances` | `map<Address, Int>` | Claimed, withdrawable balance per creator |

`SaleRecord` is `{ creator: Address, usdtAmount: Int as coins, releaseTime: Int as uint32 }`.

`releaseTime` is `uint32` — a Unix timestamp, so it overflows in 2106. Irrelevant for the intended 21-day horizon, worth knowing if the lock period is ever raised to something absurd.

## Messages

### `NewSale { saleId: uint64, creator: Address, usdtAmount: Int as coins }`

Registers a sale and starts the lock. Admin only.

- Rejects with `"Only admin can register sales"` if `sender() != admin`.
- Rejects with `"Sale amount below minimum"` if `usdtAmount < 1_000_000`.
- Writes `releaseTime = now() + 1_814_400` (21 days). The caller cannot choose the release time.
- **Overwrites** any existing record under the same `saleId`. A repeated id does not error; it replaces the earlier record, and the earlier sale's amount is lost. Ids must be unique per sale, and that is not enforced on-chain.

### `ClaimSale { saleId: uint64 }`

Moves a sale from the lock into the creator's withdrawable balance. Callable by anyone — the recipient is taken from the stored record, not from the sender.

- Rejects with `"Sale record not found"` if no record exists under `saleId`.
- Rejects with `"Funds are still in 21-day lockup"` if `now() < releaseTime`.
- Adds `usdtAmount` to `availableBalances[record.creator]` and deletes the sale record, so storage rent on historical sales stops accruing.

### `Withdraw { amount: Int as coins }`

Creator-initiated withdrawal. The destination is `sender()`, so a creator can only ever pull to their own address. The creator pays the gas for this message.

### `AdminWithdraw { creator: Address, amount: Int as coins }`

Operator-initiated withdrawal on a creator's behalf, paying the gas from the contract's own TON balance. This is what the bot calls when a creator with no TON presses withdraw.

- Rejects with `"Only admin can trigger zero-fee withdrawals"` if `sender() != admin`.
- Funds always go to `creator`, never to `admin`, so the admin cannot redirect a payout to itself through this message.

Both withdrawal paths share one internal routine, `processWithdrawal(target, amount)`:

1. Reads `availableBalances[target]`, defaulting to `0` when absent.
2. Rejects with `"Minimum withdrawal is 10 USDT"` if `amount < 10_000_000`.
3. Rejects with `"Insufficient creator balance"` if `balance < amount`.
4. Decrements `availableBalances[target]` **before** sending — the reentrancy guard.
5. Sends a `JettonTransfer` (`0x0f8a7ea5`) to `usdtWalletAddress` with `value: 0.05 TON`, `forward_ton_amount: 0.01 TON`, `response_destination: admin`, `mode: SendIgnoreErrors`.

There is no fee taken here. `amount` leaves the contract in full.

### Empty body (`receive()`)

Tops up the gas tank and emits `"Gas Tank Refilled"` into the transaction log. Send plain TON to the contract address to fund withdrawals for creators who hold no TON.

## Getters

| Getter | Returns |
|---|---|
| `balance(creator: Address)` | Withdrawable USDT base units for that creator, `0` when absent |
| `sale(saleId: Int)` | The `SaleRecord`, or `null` once claimed |
| `contractTonBalance()` | The contract's own TON balance, i.e. how much gas tank is left |

Every operation fits comfortably inside a standard 0.05 TON message value, which is why `GAS_CONSUMPTION` is set to exactly that.

## Testing

`tests/SmartStaccer.spec.ts` runs against `@ton/sandbox` with three treasury actors — `botAdmin`, `creator`, and a `mockUsdtWallet` standing in for the jetton wallet. It asserts, in order:

1. A non-admin `NewSale` is rejected.
2. An admin `NewSale` of 0.5 USDT is rejected for being under the 1 USDT minimum.
3. Two valid sales are registered, 50 USDT (`saleId` 101) and 30 USDT (`saleId` 102).
4. `ClaimSale` for 101 before `releaseTime` is rejected.
5. The sandbox clock is moved forward 22 days; both sales are claimed; `balance(creator)` becomes 80 USDT.
6. An `AdminWithdraw` of 5 USDT is rejected for being under the 10 USDT minimum.
7. An `AdminWithdraw` of 20 USDT succeeds and `balance(creator)` becomes 60 USDT.

### What the test suite does *not* cover

Worth knowing before you trust it as a complete verification:

- **The creator-initiated `Withdraw` path is never exercised.** Only `AdminWithdraw` is tested, so the branch that derives the destination from `sender()` is unverified.
- **`mockUsdtWallet` is a plain treasury, not a real jetton wallet.** The test asserts that the balance accounting is correct, not that a well-formed `JettonTransfer` reaches a USDT wallet and credits a creator. The outbound message body is never validated.
- **No re-entry test.** The decrement-before-send ordering is present in the source but is not attacked by the suite.
- **No duplicate-`saleId` test.** The overwrite behaviour described above is untested.

Run it with `npm test`. See the README for the full build sequence.
